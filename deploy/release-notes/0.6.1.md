## A recovery on Windows finishes in the same command

`peerfectly recover` made the new admin identity, signed its batch, and then stopped on Windows:
the daemon still held the network's database open, and Windows refused to copy it (os error 33).
The next start finished the swap, but into a folder no checkpoint vouched for, so the network was
not carried and the person was told it had been changed by something else.

- **The network is closed before its files move.** Its database is let go of, whoever still holds
  it, and the recovery takes up the new identity at once, with no restart. A database copied while
  open is torn on any platform, so this holds everywhere.
- **The checkpoint moves with the roster,** so the folder that takes the network's place is vouched
  for as the old one was.
- **A recovering folder is believed only through this machine's signature.** Its note names the
  network, the label and the new identity, signed by the machine's key. At start, a swap that a stop
  interrupted is finished only where the note, the identity beside it and the network's log agree.
  Before, a folder planted with a note file could make the daemon forget a network's keys and remove
  its folder; now it removes nothing and is reported.

A device whose swap already ended without a checkpoint stays uncarried: `peerfectly forget` the
network, revoke its unused identities from an admin, and be invited again.

## One name answers for one device

Two devices with one name resolve for neither. A recovery used to admit the new identity under the
device's old name even where another device held it.

- **No act signed here gives a name to a second device.** A recovery whose name another device holds
  asks first: an admin holding it can be revoked in the recovery, and the name passes; otherwise the
  device takes a free name, and is told which.
- **Two admins admitting one name apart still meet when their branches merge.** `status`, and the
  network's page in the app, say which name, which devices, and the rename that ends it.

## Invites and founder acts

- **An invite opened with the founder's words is delivered with the founder's root, and only then.**
  The device refused a delivery without it and went on waiting. `pending` lists one still waiting
  for its root; approving it again with the words signs that root alone.
- **An approval never replaces the device approving.** `approve --replace` on the device holding the
  name is refused, and points to `recover`, which is how a member becomes an admin.
- **A member signs a founder act at once,** on its copy of the roster, which reaches the network as
  soon as a device of it is up. Only a device the network revoked looks for a member to carry the
  act, every one at once, for up to 15 seconds; before, it tried them one after another, minutes
  when they were off.
- **`status` after a demotion and a recovery under the same name** said the new identity held no
  signing key until the daemon restarted. The key destroyed by the demotion is now said of the
  identity it belonged to.

## The app

- **A phone invites an admin**, and approving it asks for the founder's words.
- **An act signed with the founder's words no longer crashes the app.** The core ran it on the app's
  own thread, whose stack it overflowed; it runs on the core's own threads now. While it runs the app
  says so, and a *done* notice follows every signed act.
- **A device can be renamed from the phone,** and a recovery on the phone asks about a name another
  device holds, as the command line does.

## Updating

Replace `peerfectly` and `peerfectlyd` together, as always. Nothing in the roster or on the wire
changed: 0.6.0 and 0.6.1 devices work together. A recovery interrupted under 0.6.0 left a note this
release does not believe: its folder is reported, and a person removes it.
